# Cybermed / Readiness incident, 5 November 2026

## Finding

Cybermed run [42029696373](https://github.com/Cyberlurch/NewsAgent2/actions/runs/42029696373)
failed **before generation and SMTP**, during PubMed ingestion. Readiness run
[42030058874](https://github.com/Cyberlurch/NewsAgent2/actions/runs/42030058874)
then correctly reported missing current publication and an unreconciled failed
run. This is not the earlier scheduling false alarm and not a failed Git push
after a successful email.

Both runs used `00acd9acd18978c9fed0e80db4b41a9493bca787`; Readiness checked
that exact State commit. Times below are Europe/Stockholm (UTC+1).

| Evidence | Observed result |
| --- | --- |
| Cybermed, 13:44:27–13:46:57 | Recovery step succeeded; report step raised `pubmed_ingestion_failed:daily_delivery_blocked`; verification failed; publication step skipped. |
| PubMed diagnostics | 26 query entries: 8 `invalid_esearch_count`, 5 `server_error`, 1 `timeout`, 12 `time_budget`; 41 HTTP attempts, zero fetched records, zero model calls. Retrieval consumed approximately 120 seconds. |
| Current-run delivery result and recovery journal | Same edition `cybermed:daily:2026-11-05:2026-11-05:production`; `failed`, `not_handed_off`, no accepted/rejected/unknown recipients, no prior attempts, `generation_validated=false`, no saved generation approval. |
| Readiness, 13:47 | `cybermed:daily:operational_daily_publication_stale` and `cybermed:operational_prior_run_recovery_required`. |

The collector retries HTTP 429/5xx and transport failures, but previously
returned HTTP-200 JSON before checking ESearch fields. The eight invalid-count
responses therefore bypassed schema-error retry handling. The other observed
server errors and timeout already exhausted bounded transport retries. Later
queries had no shared retrieval time left. Ingestion marks actual source
failures as fatal, so `_main` stopped before the sender.

The diagnostic categories establish failed/unusable source responses, not
their upstream cause: raw NCBI responses were intentionally not retained.
They cannot establish a global NCBI outage, a particular malformed payload,
or whether retrying that day's responses would have recovered. The masked
NCBI key is trimmed by the collector; a trailing whitespace seen in workflow
environment logging is not evidence of the cause.

## Comparison and delivery evidence

The latest 20 repository runs were inspected, covering 2–5 November. At the
initial audit there were no runs newer than the two reported failures.
The previous successful Cybermed run was
[41830155076](https://github.com/Cyberlurch/NewsAgent2/actions/runs/41830155076)
on 4 November; its log records SMTP acceptance for one recipient at 13:34:29
and its published journal says `accepted_by_smtp`, `completed`, and
`state_persisted=true`. The 3 November receipt is also finalized.

Today's Cyberlurch run
[42028339495](https://github.com/Cyberlurch/NewsAgent2/actions/runs/42028339495)
records SMTP acceptance for one recipient at 13:38:29 and has a matching
finalized journal receipt. Its follow-up
[42028903350](https://github.com/Cyberlurch/NewsAgent2/actions/runs/42028903350)
passed. Earlier Readiness checks on 2–5 November also passed in that window.
The two newsletters therefore have different delivery outcomes on 5 November.
SMTP acceptance proves server handoff, not arrival in the recipient's inbox.

The current published journal has no 5 November Cybermed receipt. The failure
receipt exists in the uploaded recovery artifact, which Readiness deliberately
does not import. This explains its second category without implying an unknown
SMTP outcome once the artifact has been examined. Its first category remains
valid: no current Cybermed publication exists.

No workflow rerun, real email, backfill, receipt acknowledgment, production
state edit or suppression of Readiness was performed. Normal future production
recovery imports the failed receipt and validated ingestion checkpoint before
any sender, subject to the existing scope/preimage checks. It does not itself
send the missing historical edition. A retrospective issue would require a
separate reviewed decision; missing publication alone does not justify a
digest backfill or regeneration marked as historically delivered.

## Minimal correction and limits

Daily ESearch now performs response-schema validation within the existing
bounded HTTP retry loop. A transient invalid page can recover; the identical
request preserves its history and offset. HTTP and schema retries share the
same attempt, request and time budgets. Persistent errors still fail closed,
and cross-page identity/count checks, delivery guards and readiness policy
are unchanged. Cyberlurch's legacy search call is unchanged.

Regression tests cover invalid-count recovery to both a valid empty and a
nonempty result, later-page retry, mixed HTTP/schema failures, all three retry
limits, redaction, and the main-path guarantee that exhausted schema retries
cannot send, create a Daily digest, or advance the ingestion frontier. Existing
source-failure, snapshot, receipt and offline-integrity tests remain relevant.

This is a resilience correction, not a claim that code can make an unavailable
source succeed. Sustained 5xx/timeouts can still fail the run and correctly
raise readiness alarms. Offline tests do not prove live NCBI recovery, SMTP
inbox delivery, or a successful post-merge production run. The historical
failed runs remain failed. See the PR's CI results for validation of this
change; no live-send test is part of the audit.
